직접 만드는 데이터베이스

RDBMS와 NoSQL 중 무엇을 만들지, 어떤 언어로 어떤 구조로 만들지 정리한 출발점입니다. 이 문서를 기준으로 모듈 설계를 이어갑니다.

언어 Kotlin · JVM 21외부 의존성 0 (테스트 제외)단일 노드 · 단일 프로세스
결론

둘 다 하되, DB를 두 개 만들지 않는다

공통 KV 엔진 하나 위에 문서 모델과 관계형 모델을 각각 얹는 계층형 엔진을 만듭니다.

RDBMS와 NoSQL을 따로 하나씩 만들면 같은 부분(파일 I/O, WAL, 크래시 복구)을 두 번 구현하느라 시간이 가고, 정작 차이가 어디서 오는지는 흐려집니다. 실제 시스템을 보면 둘의 차이는 대부분 저장 엔진 위, 즉 데이터 모델·스키마·쿼리 언어·트랜잭션 범위에 있습니다.

저장 구조(B+tree냐 LSM-tree냐)는 그와 별개인 두 번째 축입니다. 그래서 저장 엔진도 같은 KV 인터페이스 뒤에 두 가지를 꽂아 바꿀 수 있게 만듭니다. 이렇게 하면 "관계형이라서 다른 것"과 "B+tree라서 다른 것"을 분리해서 직접 측정할 수 있습니다.

두 축은 독립적이다

흔히 "RDBMS = B+tree, NoSQL = LSM"으로 묶어 생각하지만 실제 제품은 네 칸에 모두 존재합니다.

모델 ↓ / 저장 →
B+tree (제자리 갱신)
LSM-tree (추가 후 병합)
관계형 · SQL
MySQL InnoDB, PostgreSQL** PG는 힙 + B-tree 인덱스
MyRocks, CockroachDB, TiDBSQL 행을 KV로 인코딩해 LSM에 저장
문서 · KV
MongoDB (WiredTiger), BoltDB문서 DB도 B-tree가 기본
Cassandra, RocksDB, LevelDB쓰기 처리량 중심

CockroachDB와 TiDB가 바로 이 문서가 택한 구조입니다. SQL 계층이 테이블 행을 정렬된 KV 쌍으로 바꿔 아래 엔진에 맡깁니다.

언어

Kotlin으로 만든다

이미 익숙한 언어여야 언어가 아니라 DB 개념에 시간을 씁니다. JVM은 FileChannel, force(true)(fsync), ByteBuffer.allocateDirect(오프힙), MappedByteBuffer(mmap)를 표준으로 제공하므로 바이트 단위 페이지 관리에 부족함이 없습니다. Spring은 쓰지 않습니다. 프레임워크가 감추는 부분이 곧 배워야 할 부분이기 때문입니다.

언어장점대가참고 구현
Kotlin (JVM 21)익숙함, 테스트·벤치마크 도구(JUnit 5, JMH) 성숙, sealed class로 AST/플랜 표현이 깔끔GC 일시정지가 지연 측정에 섞임, 메모리 레이아웃 직접 제어 불가H2, Apache Derby (Java)
Go참고 자료가 가장 많음, 단순한 문법, goroutine으로 동시성 실험이 쉬움새 언어 학습 비용, 제네릭·에러 처리가 장황BoltDB, Pebble, Build Your Own Database
Rust메모리·수명 직접 제어, 실제 신규 DB들의 주력 언어빌림 검사기와 DB 개념을 동시에 배우게 되어 진도가 크게 느려짐mini-lsm, sled, TiKV
C / C++교재(CMU 15-445 BusTub)와 1:1 대응메모리 버그 디버깅에 시간이 새어 나감SQLite, RocksDB, BusTub

Go 자료(Build Your Own Database 등)를 Kotlin으로 옮겨 읽는 것은 어렵지 않습니다. 오히려 그대로 복사할 수 없어서 한 번 더 이해하게 됩니다.

아키텍처

계층과 갈림길

위에서 아래로 요청이 내려갑니다. 갈림길은 두 곳뿐이고, 그 사이를 잇는 KV 인터페이스가 이 설계의 핵심 경계입니다.

INTERFACE

문서 계층collection · JSON 인코딩 · 필터 쿼리 · 보조 인덱스

핵심 경계

KvEngine 인터페이스

이 인터페이스가 흔들리지 않으면 위아래를 독립적으로 바꿀 수 있습니다. 키는 반드시 바이트 사전순 정렬을 따릅니다. 범위 스캔, SQL 인덱스, 문서 컬렉션 순회가 전부 이 성질 하나에 기대기 때문입니다.

interface KvEngine : AutoCloseable {
    fun get(key: ByteArray): ByteArray?
    fun put(key: ByteArray, value: ByteArray)
    fun delete(key: ByteArray)                       // LSM에선 tombstone, B+tree에선 실제 삭제
    fun scan(from: ByteArray, to: ByteArray?): KvIterator  // [from, to) 정렬 순회
    fun writeBatch(ops: List<WriteOp>)              // 원자적 다중 쓰기 (WAL 한 레코드)
    fun flush()                                     // 내구성 보장 지점 (fsync)
    fun stats(): EngineStats                        // 쓰기/읽기/공간 증폭 측정용
}

sealed interface WriteOp {
    data class Put(val key: ByteArray, val value: ByteArray) : WriteOp
    data class Delete(val key: ByteArray) : WriteOp
}

stats()는 처음부터 넣습니다. 비교 실험의 숫자가 전부 여기서 나옵니다(디스크에 쓴 바이트 ÷ 사용자가 쓴 바이트 등).

바이트 레이아웃

B+tree 페이지와 키 인코딩

4 KiB 슬롯 페이지

B+tree의 노드 하나 = 디스크 페이지 하나입니다. 슬롯 배열은 앞에서 뒤로, 셀(키·값)은 뒤에서 앞으로 자라고, 둘이 만나면 페이지가 가득 찬 것이라 split합니다. SQLite와 PostgreSQL이 같은 방식을 씁니다.

헤더
type · nCells
freeStart · rightPtr
슬롯 배열 →
u16 오프셋 × n
빈 공간
← 셀 영역
[keyLen|valLen|key|val]
0x0000x010freeStartfreeEnd0xFFF

모델별 키 인코딩

관계형과 문서 모델의 차이가 바이트 수준에서 드러나는 곳입니다. 관계형은 스키마를 알기 때문에 값을 열 단위로 고정 인코딩하고, 문서는 스키마가 없어서 필드 이름까지 값 안에 넣어야 합니다. 정수는 부호 비트를 뒤집은 빅엔디언으로 저장해야 바이트 정렬이 숫자 정렬과 일치합니다.

SQL 행t/00000007/r/80000000000002A → [id:int64][name:len+utf8][age:int32]
SQL 인덱스t/00000007/i/02/"kim"/80000000000002A → (비어 있음, PK가 키에 포함)
문서c/00000003/d/user-42 → {"name":"kim","tags":["a","b"],"addr":{...}}
MVCC 버전<위 키>/~commitTs → 값 · ~는 비트 반전, 최신 버전이 먼저 오게

표기는 읽기 쉽게 쓴 것이고 실제로는 구분자 대신 고정 길이 바이너리를 씁니다. 0x2A = 42.

마일스톤 순서

순서에 의미가 있습니다. 가장 단순한 영속 KV로 시작해 저장 엔진 두 개를 만들고, 한 번 비교한 뒤, 그 위에 모델을 얹고, 다시 비교합니다. 각 단계는 끝날 때 테스트로 증명할 수 있는 완료 조건이 있습니다.

차이를 숫자로 확인하는 방법

실험축측정예상되는 관찰 (검증 대상)
무작위 키 대량 쓰기B+tree LSM처리량, 디스크 쓰기 바이트LSM이 순차 쓰기라 처리량이 높지만 compaction으로 총 쓰기 바이트는 늘어남
점 조회 (없는 키 포함)B+tree LSM조회당 읽은 페이지 수bloom filter를 끄면 LSM의 없는 키 조회가 급격히 느려짐
같은 키 반복 갱신B+tree LSM디스크 사용량 추이LSM은 compaction 전까지 공간이 커졌다가 줄어드는 톱니 모양
주문 + 항목 조회관계형 문서KV get 횟수, 지연문서 임베딩은 get 1회, 관계형은 JOIN으로 여러 번
고객 이름 변경관계형 문서갱신해야 하는 키 수문서에 고객 정보를 복제해 두면 모든 주문 문서를 고쳐야 함
컬럼 추가관계형 문서마이그레이션 시간관계형은 catalog 변경 + 기존 행 해석 규칙 필요, 문서는 즉시 가능하지만 읽는 쪽이 두 형태를 처리

"예상되는 관찰"은 가설입니다. 측정해서 다르게 나오면 그쪽이 더 좋은 학습 거리입니다.

설계 착수 전 결정

먼저 못 박아 둘 것

제안값을 적어 두었습니다. 바꿔도 되지만, 바꾸면 영향받는 마일스톤을 함께 확인합니다.

페이지 크기4 KiB 고정. OS 페이지와 같아 부분 쓰기(torn write) 논의가 단순해짐
동시성M6까지 단일 쓰기 스레드. 락 설계는 M7에서 MVCC와 함께
내구성 수준커밋마다 fsync가 기본, 그룹 커밋은 옵션으로 두고 M4에서 차이 측정
