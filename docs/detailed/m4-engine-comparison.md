# M4 · 저장 엔진 비교 실험 상세 설계

> 같은 `KvEngine` 인터페이스 뒤의 세 엔진(M1 Log, M2 LSM, M3 B+tree)을 같은 워크로드로 재서, "무엇을 내주고 무엇을 얻는가"를 RUM 추측(Read · Update · Memory 중 둘만 최적화할 수 있다)의 틀로 정리한다.
> 기본 비교 표(처리량, 쓰기 증폭, 재시작, scan, 없는 키 get, 힙)는 `./gradlew :bench:run --args=compare`가 이미 채운다. M4는 그 표가 답하지 못하는 네 가지를 잰다.

## 1. 질문

| # | 질문 | 왜 기본 표로는 부족한가 |
|---|---|---|
| E1 | 키를 **무작위 순서**로 넣으면 결과가 어떻게 바뀌는가 | 기본 표는 순차 적재라 LSM 테이블들의 키 범위가 겹치지 않았고, bloom 없이도 테이블 하나만 읽었다(M2 측정 §5). B+tree도 순차 삽입은 채움률 0.5라는 특수 사례다 |
| E2 | 덮어쓰기가 계속될 때 **디스크 사용량이 시간에 따라** 어떻게 움직이는가 | 기본 표는 끝 시점 한 점만 잰다. LSM은 compaction 때마다 줄었다 느는 톱니, Log는 merge 전까지 직선 증가, B+tree는 거의 평평할 것으로 예상 |
| E3 | 매 쓰기 fsync(EVERY_WRITE) 비용을 **그룹 커밋**으로 얼마나 줄이는가 | M1에서 남긴 질문. 세 엔진 모두 `writeBatch`를 WAL 프레임 하나 + sync 한 번으로 쓰므로 엔진을 고치지 않고 배치 크기만 바꿔 잴 수 있다 |
| E4 | **읽기 증폭**: 존재하는 키 get 하나에 디스크에서 몇 바이트를 읽는가 | 기본 표는 시간만 쟀다. 재시작 직후(엔진 캐시가 빈 상태)에 엔진이 요청한 바이트를 센다 |

## 2. 실험 설계

공통: 값 100 B, 키 `key-%010d`(14 B), MANUAL 정책(E3 제외), 엔진 기본 설정(비교 측정과 같음), 한 번 실행.

### E1 무작위 순서 적재

```
키 100만 개를 Random(42) 순열 순서로 put
측정: 처리량, 쓰기 증폭, 디스크 사용량, LSM 테이블 수, B+tree 리프 평균 채움률(verify)
이어서: 없는 키 get 10만 회 (bloom 켬 / 끔), 존재하는 키 get 10만 회
```

예상:
- LSM: 처리량·쓰기 증폭은 순차와 비슷(memtable이 정렬해 주므로). **bloom 끄면 없는 키 get이 테이블 수만큼 블록을 읽는다** (순차 적재 때 4 KiB → 테이블 수 × 4 KiB).
- B+tree: 처리량이 순차보다 크게 낮음 — 버퍼 풀(4 MiB)보다 큰 트리에서 무작위 리프를 건드려 체크포인트마다 dirty 페이지가 많다. 채움률 약 0.69.
- Log: 순서와 무관.

### E2 공간 증폭 시계열

```
키 1만 개를 20번씩 덮어써 20만 회 put. 1만 회마다 디스크 사용량 기록
Log는 두 가지: merge 없음 / 5만 회마다 merge
```

공간 증폭 = 디스크 사용량 ÷ 살아 있는 데이터(1만 × 114 B ≈ 1.1 MiB).

### E3 그룹 커밋

```
EVERY_WRITE, 총 5,000건을 배치 크기 1 / 10 / 100으로 나눠 writeBatch
측정: ops/s
```

예상: fsync가 지배하므로 배치 크기에 거의 비례해 오른다(1 → 약 250, 100 → 수만). 엔진 간 차이는 배치가 커질수록 드러난다.

### E4 읽기 증폭

```
키 10만 개 적재 → close → 재시작 → 무작위 존재 키 1만 회 get
측정: get당 엔진이 디스크에서 읽은 바이트 (EngineStats.diskBytesRead 차이), get당 시간
```

예상:
- Log: 프레임 하나 ≈ 131 B
- LSM: 블록 하나 ≈ 4 KiB (bloom이 맞힌 테이블 하나) + 위양성
- B+tree: 처음엔 높이만큼 페이지(4 KiB × h), 버퍼 풀이 데워지면 리프 하나 또는 0. 1만 회 평균은 그 사이

주의: 운영체제 페이지 캐시는 비우지 못한다(macOS `purge`는 sudo 필요). 그래서 "디스크에서 읽은 바이트"는 **엔진이 요청한 바이트**이고 실제 장치 I/O가 아니다.

## 3. 구현

- `bench/src/main/kotlin/dev/mydb/bench/EngineExperiments.kt`, 실행 `./gradlew :bench:run --args=m4`
- E1의 B+tree 채움률은 `BTreeEngine.verify()`(체크포인트 포함)로 얻는다. 측정 구간 밖에서 부른다.
- 결과: `docs/measurements/m4-engine-comparison.md`에 표 + RUM 정리.

## 4. 완료 조건 (로드맵 M4)

세 가지 증폭(읽기 · 쓰기 · 공간)을 세 엔진에 대해 표로 남기고, 각 수치를 자료구조로 설명할 수 있다. 예상과 다른 값은 원인을 찾아 기록한다(못 찾으면 "미확인"으로).

## 5. 결과

[docs/measurements/m4-engine-comparison.md](../measurements/m4-engine-comparison.md). 7개 확인 항목 중 5개 적중.
- 틀린 예상: E2에서 B+tree 공간이 "거의 평평"하다고 봤으나 WAL(체크포인트 전까지 최대 16 MiB)을 빠뜨려 톱니가 나왔다.
- 실험 설계 오류: E2의 Log merge 변형을 세그먼트 64 MiB로 열어 merge할 대상이 없었다. 세그먼트 1 MiB로 다시 쟀다.
