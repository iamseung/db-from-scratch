# M1 LogEngine 측정 결과

> 측정일 2026-10-14 · 브랜치 `feature/m1-measurements` · 재현: `./gradlew :bench:run --args=m1` (약 2분 20초)
> 측정 코드: [`bench/src/main/kotlin/dev/mydb/bench/LogEngineBench.kt`](../../bench/src/main/kotlin/dev/mydb/bench/LogEngineBench.kt)

## 환경

| 항목 | 값 |
|---|---|
| CPU | Apple M4 Pro, 14코어 |
| 메모리 | 48 GiB |
| OS | macOS 26.6.2 |
| 디스크 | 내장 SSD, APFS |
| JDK | Corretto 21.0.5, `-Xmx4g` |

한 번 실행한 결과다. 처리량만 3회 측정해 중앙값을 썼고, 나머지는 1회 값이라 수십 % 수준의 흔들림은 의미 있게 해석하지 않는다.

## 1. put 처리량 (값 100 B)

| 정책 | 건수 | 회차별 ops/s | 중앙값 ops/s | 건당 |
|---|---:|---|---:|---:|
| EVERY_WRITE | 10,000 | 253 / 260 / 255 | 255 | 3,911 µs |
| MANUAL | 1,000,000 | 623,872 / 637,695 / 643,670 | 637,695 | 1.57 µs |

**두 정책의 차이는 약 2,500배다.** 쓰기 한 건의 실제 작업(직렬화 + `write()` 시스템 콜)은 1.6 µs이고, 나머지 3.9 ms는 전부 디스크 확정을 기다리는 시간이다.

이 3.9 ms가 어디서 오는지 C로 따로 쟀다 ([`bench/fsync/fsync_bench.c`](../../bench/fsync/fsync_bench.c), 131 B append 후 동기화 2,000회 평균):

| 호출 | 쓰기당 |
|---|---:|
| `fsync(fd)` | 21 µs |
| `fcntl(fd, F_FULLFSYNC)` | 3,824 µs |
| Java `FileChannel.force(true)` (위 EVERY_WRITE) | 3,911 µs |

Java 수치는 `F_FULLFSYNC`와 일치한다. OpenJDK 21 소스(`src/java.base/macosx/native/libnio/ch/FileDispatcherImpl.c`의 `force0`)도 macOS에서 `fcntl(fd, F_FULLFSYNC)`를 호출하고 실패할 때만 `fsync`로 물러난다.

- macOS의 `fsync`는 데이터를 디스크 컨트롤러까지만 보내고 디스크 자체 쓰기 캐시는 비우지 않는다. `F_FULLFSYNC`는 그 캐시까지 비운다. 180배 차이가 그 비용이다.
- 즉 Java는 macOS에서 전원 차단까지 보장하는 쪽을 골랐다. **M0 설계 문서는 처음에 반대로 적었다가 이 측정으로 고쳤다.**
- 다음 질문: 쓰기 여러 건을 모아 `force()` 한 번으로 확정하면(그룹 커밋) 처리량이 얼마나 오르는가 → M4.

## 2. 쓰기 증폭과 merge

키 1만 개를 10번씩 덮어써 10만 건 put (값 100 B), 그 뒤 merge. 세그먼트 1 MiB.

| 시점 | 사용자 바이트 | 디스크에 쓴 바이트 | 쓰기 증폭 | 디스크 사용량 |
|---|---:|---:|---:|---:|
| merge 전 | 10.9 MiB | 12.5 MiB | 1.149 | 12.5 MiB |
| merge 후 | 10.9 MiB | 13.2 MiB | 1.219 | 1.2 MiB |

merge: 세그먼트 12개 → 1개, 살아 있는 엔트리 6,048, 12.0 MiB → 0.8 MiB

- **merge 전 1.149**는 순수하게 포맷 오버헤드다. 사용자 바이트 114 B(키 14 + 값 100)가 프레임 131 B(프레임 헤더 8 + 레코드 헤더 9)가 된다. 131 / 114 = 1.149.
- **merge가 디스크 사용량을 10분의 1로** 줄였다. 덮어쓴 옛 값 9만 건이 사라졌다.
- 그 대가로 쓰기 증폭이 1.219로 올랐다. 살아 있는 값을 한 번 더 썼기 때문이다. merge를 자주 할수록 공간은 아끼고 쓰기는 늘어난다. 이 균형이 M2(LSM compaction)의 핵심 주제다.
- 살아 있는 엔트리가 1만이 아니라 6,048인 이유: 나머지 키의 최신 값은 활성 세그먼트에 있어 merge 대상이 아니다.

## 3. 재시작 시간 (keydir 재구성)

값 1 KiB. 쓰고 닫은 직후 다시 연 시간이라 데이터가 OS 페이지 캐시에 있는 상태(warm)다.

| 데이터 크기 | 키 수 | open 시간 | 처리 속도 |
|---:|---:|---:|---:|
| 100.6 MiB | 100,000 | 0.12 s | 806 MiB/s |
| 1006.1 MiB | 1,000,000 | 1.11 s | 904 MiB/s |

- 데이터 크기에 비례한다(10배 → 9.3배). 복구는 모든 세그먼트를 처음부터 끝까지 읽어야 하기 때문이다.
- 1 GiB에 1.1초면 학습용으로는 충분하다. 다만 100 GiB면 warm 상태로도 약 2분이다. Bitcask가 keydir 스냅샷(hint 파일)을 두는 이유다. **hint 파일은 계속 만들지 않는다.**
- cold cache(디스크에서 직접 읽기)는 재지 못했다. macOS에서 페이지 캐시를 비우려면 `sudo purge`가 필요하다.

## 4. scan 비용 vs 전체 키 수 (범위 100건 고정)

scan 200회 평균. 비교를 위해 같은 100개 키를 get으로 하나씩 읽은 시간도 쟀다.

| 전체 키 수 | scan 1회 (100건) | get 100회 (같은 키) | scan / get |
|---:|---:|---:|---:|
| 10,000 | 0.278 ms | 0.103 ms | 2.7배 |
| 100,000 | 4.097 ms | 0.113 ms | 36배 |
| 1,000,000 | 16.139 ms | 0.132 ms | 122배 |

- **get은 키 수와 무관하게 일정**하고, **scan은 결과가 100건으로 같아도 전체 키 수와 함께 커진다.** 정렬되지 않은 HashMap에서 범위를 찾으려면 전체 키를 훑어야 하기 때문이다(상세 설계 §6.2에서 의도한 약점).
- 증가율이 정확히 선형은 아니다(10배 → 14.7배, 10배 → 3.9배). 원인은 조사하지 않았다. 값 하나를 읽는 비용이 아니라 전체 키를 훑는 비용이 지배한다는 결론은 바뀌지 않는다.
- M2의 SSTable은 키가 정렬되어 있어 시작 위치를 찾은 뒤 100건만 읽으면 된다. M4에서 같은 표를 다시 채워 비교한다.

## 5. keydir 힙 사용량 (키 100만 개, 키 14 B)

| 키 수 | 힙 증가 | 키당 |
|---:|---:|---:|
| 1,000,000 | 124.4 MiB | 130 B |

키 자체는 14 B인데 키당 130 B가 든다. 아래는 HotSpot 64비트 + compressed oops 기준의 **추정** 내역이다(객체별로 직접 잰 값이 아님). 합계 약 128 B로 측정값과 맞는다.

| 객체 | 추정 크기 |
|---|---:|
| `BytesKey` (헤더 12 + 배열 참조 4 + hash 4, 8바이트 정렬) | 24 B |
| 키 `byte[14]` (헤더 16 + 14, 정렬) | 32 B |
| `Location` (헤더 12 + int 3개 + long 1개, 정렬) | 32 B |
| `HashMap.Node` (헤더 12 + hash·key·value·next) | 32 B |
| HashMap 버킷 배열 (2^21칸 × 4 B ÷ 100만) | 약 8 B |

- 키 길이가 짧을수록 객체 오버헤드 비중이 커진다. 키 14 B 기준 약 9배.
- 모든 키가 메모리에 있어야 한다는 Bitcask의 제약이 숫자로는 이 정도다. 1억 키면 약 12 GiB.
- M2(LSM)는 keydir 대신 SSTable 안의 희소 인덱스만 메모리에 두므로 이 비용이 키 수가 아니라 블록 수에 비례한다.

| 질문 (상세 설계 §1) | 측정이 준 답 |
|---|---|
| 추가 전용 쓰기는 왜 빠른가 | 쓰기 자체는 1.6 µs. 느린 건 쓰기가 아니라 확정(fsync)이다 |
| 로그가 무한히 커지는 문제 | merge로 디스크 사용량 1/10, 대신 쓰기 증폭 +0.07 |
| 해시 인덱스로는 왜 범위 스캔이 비싼가 | 100건 scan이 키 100만 개에서 get보다 122배 느림 |
| 모든 키를 메모리에 둔다는 것의 비용 | 키 14 B당 130 B |
