# M2 측정: M1 LogEngine vs M2 LsmEngine

> 측정일 2026-10-25 · 재현: 당시 `--args=m2`(두 엔진). 지금은 `./gradlew :bench:run --args=compare`가 M3까지 함께 잰다 · 코드: [`CompareBench.kt`](../../bench/src/main/kotlin/dev/mydb/bench/CompareBench.kt)
> 환경은 [M1 측정](m1-log-engine.md)과 같다 (M4 Pro, APFS, Corretto 21, `-Xmx4g`). 두 엔진을 **같은 실행**에서 같은 시나리오로 쟀다.
> 설정: M1 세그먼트 64 MiB / M2 memtable 1 MiB, 블록 4 KiB, bloom 10 bits/key, size-tiered 최소 4개.

## 요약: 설계 §15 예상과 비교

| 항목 | 예상 | 실측 | 판정 |
|---|---|---|---|
| put 처리량 (MANUAL) | M1과 비슷하거나 약간 낮음 | M1 654,638 / **M2 185,357 ops/s (3.5배 낮음)** | ❌ 틀림 → 아래 §1 |
| 쓰기 증폭 (서로 다른 키 100만) | 약 5 | **5.32** | ✅ |
| scan 100건, 키 100만 | M1 16 ms보다 크게 낮음 | 15.1 ms → **0.016 ms** (약 940배) | ✅ |
| 없는 키 get | bloom 없으면 테이블당 블록 읽기 | bloom: 0.63 µs, **33 B** / 없음: 1.99 µs, **4,031 B** | ✅ |
| 키 100만 개 힙 | 키당 수 B | **키당 2 B** (M1 130 B) | ✅ |
| 재시작 | 데이터 크기와 거의 무관 | 100 MiB **16 ms**, 1 GiB **26 ms** (M1 0.1 s, 1.0 s) | ✅ |

## 1. put 처리량 (값 100 B)

| 엔진 | 정책 | 건수 | 회차별 ops/s | 대표 ops/s |
|---|---|---:|---|---:|
| M1 Log | MANUAL | 1,000,000 | 575,126 / 670,428 / 654,638 | 654,638 |
| M1 Log | EVERY_WRITE | 5,000 | 247 | 247 |
| M2 LSM | MANUAL | 1,000,000 | 185,357 / 185,080 / 185,704 | 185,357 |
| M2 LSM | EVERY_WRITE | 5,000 | 259 | 259 |

- **EVERY_WRITE는 두 엔진이 같다** (약 250 ops/s). 쓰기 한 건마다 `F_FULLFSYNC` 3.9 ms가 지배해서 엔진 구조 차이가 보이지 않는다.
- **MANUAL에서 M2가 3.5배 느리다.** 예상이 틀렸다. M2는 put 하나에 WAL 쓰기 외에도 백그라운드 없이 쓰기 스레드가 직접 하는 일이 있다:
  - **compaction이 데이터를 다시 쓴다.** 쓰기 증폭 5.32 = 사용자 109 MiB에 대해 디스크 578 MiB. M1은 1.15(125 MiB)다. 디스크에 쓰는 양만 4.6배다.
  - **flush마다 fsync가 몇 번씩 든다.** memtable 1 MiB마다 SSTable sync, rename 후 디렉터리 sync, 새 WAL 디렉터리 sync, MANIFEST sync가 있고, compaction도 SSTable·MANIFEST sync를 한다. MANUAL 정책이어도 이 sync들은 commit point라 생략하지 않는다(설계 §7).
  - 이 둘의 비중은 프로파일링하지 않아 **나누지 못했다**. 다만 M1과의 디스크 쓰기량 차이(4.6배)가 처리량 차이(3.5배)와 같은 크기라, compaction이 주 원인으로 보인다.
- 예상을 세울 때 "memtable 삽입 비용"만 보고 **compaction을 쓰기 경로에서 동기로 한다**는 결정(설계 §2)의 비용을 빠뜨렸다. 실제 LSM 엔진이 compaction을 백그라운드로 돌리는 이유다.

## 2. 쓰기 증폭과 디스크 사용량

| 엔진 | 워크로드 | 사용자 바이트 | 디스크에 쓴 바이트 | 쓰기 증폭 | 디스크 사용량 | 테이블 수 |
|---|---|---:|---:|---:|---:|---:|
| M1 Log | 서로 다른 키 100만 | 108.7 MiB | 124.9 MiB | 1.15 | 124.9 MiB | - |
| M1 Log | 키 1만 × 10회 덮어쓰기 | 10.9 MiB | 12.5 MiB | 1.15 | 12.5 MiB | - |
| M2 LSM | 서로 다른 키 100만 | 108.7 MiB | 577.9 MiB | **5.32** | 118.8 MiB | 7 |
| M2 LSM | 키 1만 × 10회 덮어쓰기 | 10.9 MiB | 28.3 MiB | 2.61 | **2.0 MiB** | 1 |

- 서로 다른 키: 설계 §9.3의 계산(WAL 1 + flush 1 + compaction 약 3.3단계 ≈ 5)과 맞는다.
- 덮어쓰기: compaction이 옛 값을 계속 버려서 디스크 사용량이 M1의 1/6이다. M1은 merge를 부르지 않으면 공간이 계속 는다. M2는 쓰기를 더 하는 대신 공간을 자동으로 회수한다. **쓰기 증폭 ↔ 공간 증폭 교환**이 숫자로 보인다.

## 3. 재시작 시간 (값 1 KiB, warm cache)

| 엔진 | 데이터 | open 시간 |
|---|---:|---:|
| M1 Log | 100.6 MiB | 0.108 s |
| M1 Log | 1006.1 MiB | 1.007 s |
| M2 LSM | 101.2 MiB | 0.016 s |
| M2 LSM | 1012.2 MiB | 0.026 s |

M1은 모든 세그먼트를 읽어 keydir를 다시 만든다(크기에 비례). M2는 MANIFEST 재생 + 테이블마다 footer·인덱스·bloom 로드 + 마지막 WAL(최대 1 MiB) 재생이라 데이터 크기와 거의 무관하다.

## 4. scan 100건 vs 전체 키 수 (200회 평균)

| 엔진 | 전체 키 | scan 1회 | get 100회 (같은 키) | 테이블 수 |
|---|---:|---:|---:|---:|
| M1 Log | 10,000 | 0.319 ms | 0.106 ms | - |
| M1 Log | 100,000 | 3.705 ms | 0.109 ms | - |
| M1 Log | 1,000,000 | 15.091 ms | 0.104 ms | - |
| M2 LSM | 10,000 | 0.028 ms | 0.189 ms | 1 |
| M2 LSM | 100,000 | 0.017 ms | 0.214 ms | 4 |
| M2 LSM | 1,000,000 | 0.016 ms | 0.236 ms | 7 |

- **scan은 M2가 키 수와 무관하게 일정하고, 100만 키에서 M1보다 약 940배 빠르다.** 정렬된 SSTable에서 시작 블록을 찾은 뒤 블록 몇 개만 읽는다.
- **반대로 get은 M2가 2.3배 느리다** (2.4 µs vs 1.0 µs). M1은 keydir에서 위치를 바로 찾아 프레임 하나를 읽지만, M2는 memtable → 테이블마다 범위 검사·bloom → 인덱스 이진 탐색 → **4 KiB 블록 전체를 읽고 디코딩**한다. 블록 캐시가 없어서(설계 §2) 같은 블록을 매번 다시 디코딩한다.
- scan 100건이 get 100번보다 15배 빠르다. 연속 키를 블록 단위로 한 번에 읽기 때문이다.

## 5. 없는 키 get (키 100만 개 적재 후 10만 회)

| 엔진 | bloom | 테이블 수 | get 1회 | get당 디스크 읽기 |
|---|---|---:|---:|---:|
| M1 Log | - | - | 0.11 µs | 0 B |
| M2 LSM | 10 bits/key | 7 | 0.63 µs | 33 B |
| M2 LSM | 없음 | 7 | 1.99 µs | 4,031 B |

- **33 B = 위양성률 × 블록 크기**: 0.8% × 4 KiB ≈ 33 B. bloom 테스트에서 잰 위양성률(0.816%)이 실제 읽기량에 그대로 나타났다.
- bloom이 없으면 get마다 블록 하나(약 4 KiB)를 읽는다. 테이블이 7개인데 블록 **하나**인 이유: 키를 순서대로 넣어서 테이블들의 키 범위가 겹치지 않고, `[minKey, maxKey]` 검사가 한 테이블만 남긴다. 무작위 순서로 넣으면 범위가 겹쳐 bloom 없이 테이블 수만큼 읽게 된다(M4에서 확인).
- M1은 없는 키를 keydir(메모리)에서 바로 판정한다. 메모리를 키당 130 B 쓰는 대가다.

## 6. 키 100만 개 힙 (키 14 B, 값 100 B)

| 엔진 | 힙 증가 | 키당 | 테이블 수 |
|---|---:|---:|---:|
| M1 Log | 124.5 MiB | 130 B | - |
| M2 LSM | 2.8 MiB | **2 B** | 7 |

M2의 내역(추정): 블록 인덱스 약 2.9만 블록 × (키 14 B + offset 8 B + 배열 오버헤드) ≈ 1.1 MiB, bloom 100만 × 10 bit = 1.2 MiB, 나머지는 memtable. 키 수가 아니라 블록 수에 비례하는 구조라 M1의 1/65다.

## 정리: M1 → M2에서 얻은 것과 낸 것

| 얻은 것 | 낸 것 |
|---|---|
| scan 940배 빠름 (키 수 무관) | 쓰기 증폭 1.15 → 5.32 |
| 힙 130 B → 2 B/키 | MANUAL put 처리량 3.5배 낮음 (동기 compaction) |
| 재시작 시간이 데이터 크기와 무관 | 존재하는 키 get 2.3배 느림 (블록 캐시 없음) |
| 덮어쓰기 워크로드 공간 자동 회수 (1/6) | 없는 키 판정에 bloom(확률적) 필요 |

M3(B+tree)는 이 표의 "낸 것" 중 get 성능과 쓰기 경로 단순함을 되찾는 대신 무엇을 내는지 같은 표로 잰다.
