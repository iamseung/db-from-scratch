# M3 측정: M1 Log · M2 LSM · M3 B+tree

> 측정일 2026-10-25 · 재현: `./gradlew :bench:run --args=compare` (약 10분) · 코드: [`CompareBench.kt`](../../bench/src/main/kotlin/dev/mydb/bench/CompareBench.kt)
> 환경은 [M1 측정](m1-log-engine.md)과 같다. 세 엔진을 같은 실행에서 같은 시나리오로 쟀다.
> 설정: Log 세그먼트 64 MiB / LSM memtable 1 MiB·블록 4 KiB·bloom 10 bits·size-tiered 4 / B+tree 페이지 4 KiB·버퍼 풀 1024장(4 MiB)·체크포인트 WAL 16 MiB.
> M2 측정 때와 달리 재시작 시나리오의 값은 1,000 B다 (B+tree 셀 상한 1,014 B에 맞춤).

## 요약: M3 설계 §10·§13 예상과 비교

| 항목 | 예상 | 실측 | 판정 |
|---|---|---|---|
| put 처리량 MANUAL | M1·M2보다 낮음 | 102,361 ops/s (M1 637k, M2 187k) | ✅ |
| 쓰기 증폭: 순차 삽입 | 약 3 | **5.39** | ❌ 채움률을 빠뜨림 (아래 §2) |
| 쓰기 증폭: 무작위 갱신 | 수십 (4096 × 2 / 114 ≈ 72) | **67.08** | ✅ |
| scan 100건 | M2와 비슷하거나 빠름 | 키 1만: 0.013 ms (M2 0.040) / 키 100만: 0.036 ms (M2 0.019) | △ 규모가 커지면 M2보다 느림 |
| 없는 키 get | 존재하는 키와 같은 비용 | 6.17 µs vs 존재 키 4.57 µs | ✅ (같은 경로, 같은 차수) |
| 키 100만 힙 | 버퍼 풀 크기로 고정 | 4.1 MiB, 키당 4 B | ✅ |
| 재시작 | 마지막 체크포인트 이후 WAL 재생 | 196 MiB 34 ms / 1.97 GiB 27 ms | ✅ 데이터 크기와 무관 |

## 1. put 처리량 (값 100 B)

| 엔진 | MANUAL ops/s (3회) | EVERY_WRITE ops/s |
|---|---|---:|
| M1 Log | 627,705 / 637,350 / 652,647 | 264 |
| M2 LSM | 184,128 / 187,713 / 186,703 | 284 |
| M3 B+tree | 99,854 / 102,424 / 102,361 | 263 |

EVERY_WRITE는 세 엔진이 같다 (쓰기마다 `F_FULLFSYNC` 3.9 ms). MANUAL에서 B+tree가 가장 느린 이유: 삽입마다 페이지 안 슬롯 배열을 밀어내고(memmove), 리프가 차면 split하며, 버퍼 풀(4 MiB)이 dirty 페이지로 차거나 WAL이 16 MiB가 될 때마다 체크포인트(doublewrite + 제자리 + fsync 여러 번)를 한다. 각 비중은 프로파일링하지 않았다.

## 2. 쓰기 증폭과 디스크 사용량

| 엔진 | 워크로드 | 사용자 | 디스크에 씀 | 쓰기 증폭 | 디스크 사용량 |
|---|---|---:|---:|---:|---:|
| M1 Log | 서로 다른 키 100만 (순차) | 108.7 MiB | 124.9 MiB | 1.15 | 124.9 MiB |
| M2 LSM | 〃 | 108.7 MiB | 577.9 MiB | 5.32 | 118.8 MiB |
| M3 B+tree | 〃 | 108.7 MiB | 586.3 MiB | **5.39** | **230.9 MiB** |
| M1 Log | 키 1만 × 10회 덮어쓰기 | 10.9 MiB | 12.5 MiB | 1.15 | 12.5 MiB |
| M2 LSM | 〃 | 10.9 MiB | 28.3 MiB | 2.61 | 2.0 MiB |
| M3 B+tree | 〃 | 10.9 MiB | 12.5 MiB | 1.15 | 12.5 MiB |
| M1 Log | 키 10만 적재 후 무작위 갱신 10만 (갱신 구간만) | 10.9 MiB | 12.5 MiB | 1.15 | 25.0 MiB |
| M2 LSM | 〃 | 10.9 MiB | 45.5 MiB | 4.19 | 20.9 MiB |
| M3 B+tree | 〃 | 10.9 MiB | 729.3 MiB | **67.08** | 23.3 MiB |

**순차 삽입 5.39 — 예상(약 3)이 틀린 이유**: 예상은 "페이지가 꽉 찬다"고 가정했다. 실제로 순차 삽입은 리프 채움률이 0.51이다(오른쪽 끝에서만 split, M3 설계 §11.2). 그래서 페이지 바이트가 사용자 데이터의 약 2.1배(디스크 231 MiB / 109 MiB)이고, 체크포인트가 그 페이지를 doublewrite와 제자리로 두 번 쓴다: 1.15(WAL) + 2 × 2.1 ≈ 5.4. 실측과 맞는다. 같은 이유로 **공간 증폭도 2.1배**다.

**무작위 갱신 67 — B+tree의 약점이 숫자로**: 키 10만 개 트리(약 23 MiB)가 버퍼 풀(4 MiB)보다 커서, 무작위 갱신 하나가 거의 매번 다른 리프를 dirty로 만든다. 버퍼 풀이 dirty로 차면 체크포인트가 그 리프들을 4 KiB씩 두 번 쓴다. 114 B를 바꾸려고 약 8 KiB를 쓴다. 같은 워크로드에서 LSM은 4.19다. **LSM이 무작위 쓰기를 순차 쓰기로 바꾸는 이유가 이 16배 차이다.**

**덮어쓰기 1.15**: 키 1만 개 트리(약 2 MiB)는 버퍼 풀에 다 들어가고 WAL이 16 MiB에 못 미쳐 측정 중 체크포인트가 한 번도 일어나지 않았다. 디스크에 간 것은 WAL뿐이다. 체크포인트(또는 재시작)가 오면 그때 페이지를 쓴다.

## 3. 재시작 시간 (값 1,000 B, warm cache)

| 엔진 | 데이터 | open |
|---|---:|---:|
| M1 Log | 98 MiB / 983 MiB | 0.115 s / 1.066 s |
| M2 LSM | 99 MiB / 986 MiB | 0.018 s / 0.021 s |
| M3 B+tree | 196 MiB / 1,973 MiB | 0.034 s / 0.027 s |

B+tree는 meta 페이지를 읽고 마지막 체크포인트 이후 WAL(최대 16 MiB)만 재생한다. 데이터 크기와 무관하다. 값이 1,000 B면 리프에 셀이 3~4개라 순차 삽입에서도 디스크가 사용자 데이터의 2배다.

## 4. scan 100건 vs 전체 키 수

| 엔진 | 키 1만 | 키 10만 | 키 100만 | get 100회 (키 100만) |
|---|---:|---:|---:|---:|
| M1 Log | 0.308 ms | 1.022 ms | 10.678 ms | 0.104 ms |
| M2 LSM | 0.040 ms | 0.017 ms | 0.019 ms | 0.216 ms |
| M3 B+tree | 0.013 ms | 0.040 ms | 0.036 ms | 0.457 ms |

- 키 1만(트리 전체가 버퍼 풀 안)에서는 B+tree가 가장 빠르다: 리프 몇 장을 메모리에서 읽는다.
- 키 10만 이상에서는 트리가 버퍼 풀보다 커서 리프를 디스크(실제로는 OS 캐시)에서 읽고 체크섬을 검사한다. get 100회가 M2의 2배 걸리는 것도 같은 이유다. **블록 캐시가 없는 M2와 버퍼 풀이 작은 M3의 차이**로, 버퍼 풀을 키우면 순위가 바뀔 수 있다(M4 E4에서 읽기 바이트로 확인).

## 5. 없는 키 get (키 100만)

| 엔진 | get 1회 | get당 읽기 |
|---|---:|---:|
| M1 Log | 0.12 µs | 0 B (keydir가 메모리에서 판정) |
| M2 LSM, bloom | 0.42 µs | 33 B (위양성률 0.8% × 4 KiB) |
| M2 LSM, bloom 없음 | 1.87 µs | 4,031 B |
| M3 B+tree | 6.17 µs | 2,405 B |

B+tree는 없는 키도 루트에서 리프까지 내려가 봐야 안다. get당 2.4 KiB는 "높이 3 중 평균 0.6장이 버퍼 풀에 없었다"는 뜻이다. bloom 같은 사전 필터가 없는 구조의 비용이다.

## 6. 키 100만 힙

| 엔진 | 키당 |
|---|---:|
| M1 Log | 130 B (모든 키가 keydir에) |
| M2 LSM | 2 B (블록 인덱스 + bloom + memtable) |
| M3 B+tree | 4 B (버퍼 풀 4 MiB 고정, 키 수와 무관) |

## 정리 — 세 엔진의 교환

| | 잘하는 것 | 내주는 것 |
|---|---|---|
| M1 Log | 쓰기 (1.15), 점 조회 (메모리 인덱스) | 메모리 (130 B/키), scan (전체 순회), 재시작 (크기 비례), 공간 (merge 전까지 증가) |
| M2 LSM | 무작위 쓰기 증폭 (4.2), 메모리, scan, 재시작 | 순차 쓰기 증폭 (5.3), 동기 compaction 처리량, 점 조회에 블록 디코딩 |
| M3 B+tree | 작은 데이터의 scan·조회, 재시작, 메모리 고정 | **무작위 갱신 쓰기 증폭 (67)**, 순차 삽입 공간 (2.1배), 처리량 |

M4는 이 표에 무작위 순서 적재, 공간 증폭 시계열, 그룹 커밋, 읽기 증폭을 더해 RUM 관점으로 정리한다.
