# M7 측정: MVCC 트랜잭션

> 측정일 2026-10-25 · 재현: `./gradlew :bench:run --args=m7` · 코드: [`TxnBench.kt`](../../bench/src/main/kotlin/dev/mydb/bench/TxnBench.kt)
> 설계: [m7-transactions.md](../detailed/m7-transactions.md). 엔진 MANUAL 정책, 기본 설정, 1회 측정.

## 1. 트랜잭션 크기별 커밋 비용 (총 키 쓰기 2만 건)

| 엔진 | 트랜잭션당 키 | 트랜잭션/s | 키 쓰기/s |
|---|---:|---:|---:|
| M1 Log | 1 / 10 / 100 | 9,380 / 917 / 124 | 9,380 / 9,177 / 12,429 |
| M2 LSM | 1 / 10 / 100 | 79,290 / 12,972 / 1,831 | 79,290 / 129,721 / 183,178 |
| M3 B+tree | 1 / 10 / 100 | 105,196 / 19,913 / 1,864 | 105,196 / 199,137 / 186,443 |

- **트랜잭션이 클수록 키당 비용이 내려간다** (LSM 7.9만 → 18.3만 키/s). 커밋마다 고정 비용(잠금, `t/last` 갱신, writeBatch 1회)이 있고 키 수로 나눠지기 때문이다. 충돌 검사는 키마다 범위 scan 하나라 키 수에 비례한다.
- **M1 위의 MVCC는 느리다** (키 쓰기 약 1만/s). 버전 읽기와 충돌 검사가 모두 범위 scan인데, M1의 scan은 정렬되지 않은 keydir 전체를 훑는다. MVCC는 **정렬된 저장 엔진**을 전제로 한다.

## 2. 버전 누적과 GC (키 1,000개를 각각 N번 갱신)

| 엔진 | 키당 버전 | get (GC 전) | GC가 지운 버전 | get (GC 후) | GC 후 정리 | get (정리 후) |
|---|---:|---:|---:|---:|---|---:|
| M1 Log | 1 / 10 / 100 | 5.3 / 49.9 / 476.7 µs | 0 / 9,000 / 99,000 | 5.3 / 9.9 / 82.8 µs | - | 5.2 / 10.1 / 84.3 µs |
| M2 LSM | 1 / 10 / 100 | 0.71 / 2.33 / 9.51 µs | 0 / 9,000 / 99,000 | 0.58 / 3.70 / **11.99** µs | compactAll | 2.77 / 3.62 / **1.91** µs |
| M3 B+tree | 1 / 10 / 100 | 0.55 / 2.07 / 26.81 µs | 0 / 9,000 / 99,000 | 0.52 / 1.93 / **23.51** µs | 리프 66 → 468 → **6,000장, 채움 0.49 → 0.07 → 0.01** | 0.52 / 1.92 / 13.55 µs |

- **버전이 쌓이면 읽기가 느려진다.** 스냅샷 읽기는 `(K, readTs)` 위치에서 scan을 시작하는데, 같은 키의 버전들이 엔진 안에서 공간을 차지하기 때문이다(B+tree 0.55 → 26.8 µs).
- **GC로 지워도 바로 빨라지지 않는다 — 엔진마다 이유가 다르다.**
  - LSM: 삭제는 tombstone 쓰기다. 지운 버전과 tombstone이 compaction 전까지 물리적으로 남아, GC 직후 오히려 조금 느려졌다(9.5 → 12.0 µs). `compactAll` 후 **1.9 µs**로 떨어져 원인이 tombstone이었음을 확인했다.
  - B+tree: merge가 없어(M3 설계 §2) 셀만 지워진 리프 6,000장이 남는다(평균 채움 1%). 범위 scan이 빈 리프를 따라 걷는다. **M3의 "merge 안 함" 결정의 비용이 MVCC에서 드러났다.**
  - M1: GC 후 약 6배 빨라졌지만 버전 1개일 때보다 여전히 16배 느리다. **원인 미확인.**

## 정리

| 질문 (설계 §1) | 측정이 준 답 |
|---|---|
| 여러 행을 원자적으로 바꾸는 비용 | 커밋당 고정 비용 + 키당 충돌 검사 scan. 큰 트랜잭션일수록 키당 싸다 |
| lost update · write skew | 테스트로 재현 (lost update는 막히고 write skew는 일어남, materialize로 막힘) — [설계 §6](../detailed/m7-transactions.md) |
| 옛 버전은 언제 지울 수 있는가 | 가장 오래된 활성 스냅샷보다 오래된 버전. 단, 지운 공간을 실제로 회수하는 것은 저장 엔진(compaction, merge)의 몫 |
