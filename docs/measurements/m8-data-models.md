# M8 측정: 관계형 vs 문서형

> 측정일 2026-10-25 · 재현: `./gradlew :bench:run --args=m8` · 코드: [`DataModelBench.kt`](../../bench/src/main/kotlin/dev/mydb/bench/DataModelBench.kt)
> 설계: [m8-data-models.md](../detailed/m8-data-models.md). 두 모델 모두 같은 M2 LSM 엔진(MANUAL) 위. KV 연산 수는 `CountingKvEngine`이 센 값이다.
> 데이터: 고객 2,000 · 주문 20,000 · 주문당 항목 1 ~ 5개(총 60,000). 문서형은 주문 문서에 고객 정보와 항목을 임베딩한다.

## 요약

| # | 질문 | 관계형 | 문서형 | 예상과 비교 |
|---|---|---|---|---|
| D1 | 주문 + 항목 읽기 | get 6 · scan 1, **75 µs** | get 1, **6 µs** | ✅ 임베딩이 12배 빠름 |
| D2 | 고객 이름 변경 | 쓰기 **1**건, 26 µs | 쓰기 **10**건(주문 수), 179 µs | ✅ 복제의 대가 |
| D3 | 필드 추가 | 20,002건 재작성, **36 ms** | 0 (새 문서에만), 0.2 ms | ✅ |
| D4 | 저장 크기 | **5.9 MiB** | **4.4 MiB** | ⚠️ 반만 맞음 — 값은 관계형이 작지만 키·인덱스가 늘어 전체는 더 큼 |
| D5 | 일관성 경계 | 두 번째 문장 실패 시 **항목 없는 주문**이 남음 | 문서 단위로 전부 / 전무 | ✅ 테스트로 확인 |

## D1. 주문 하나 + 그 항목 읽기 (주문 1,000건 평균)

```
Project o.id, o.total, i.product, i.qty, i.price
  Filter o.id = 0
    IndexLookupJoin o.id → i.order_id
      Filter o.id = 0
        PkLookup orders o (id = 0)
```

| 모델 | get | scan | scan 항목 | 시간 |
|---|---:|---:|---:|---:|
| 관계형 (JOIN) | 6.0 | 1.0 | 3.0 | 75.1 µs |
| 문서형 (임베딩) | 1.0 | 0 | 0 | 6.0 µs |

관계형 get 6회 = 주문 행 1 + 인덱스로 찾은 항목 행 3 + **카탈로그 조회 2**(문장마다 테이블 정의를 KV에서 읽는다 — M6는 카탈로그를 캐시하지 않는다). 시간 차이에는 SQL 파싱·플래닝도 들어 있다. 문서형은 문서 키 하나를 읽고 JSON을 파싱하면 끝이다.

## D2. 고객 이름 바꾸기 (고객 100명 평균, 고객당 주문 10건)

| 모델 | 쓴 KV 연산 | 쓴 바이트 | 읽기 (get + scan 항목) | 시간 |
|---|---:|---:|---:|---:|
| 관계형 | 1.0 | 48 B | 2.0 | 26.1 µs |
| 문서형 | 10.0 | 2,106 B | 30.0 | 179.4 µs |

문서형은 고객 정보를 주문마다 복제했으므로, 이름 하나를 바꾸려면 그 고객의 주문 문서를 **모두 찾아(인덱스) 통째로 다시 써야** 한다. 쓰기 바이트가 44배다. 그리고 이 10건은 원자적이지 않다 — 중간에 실패하면 일부 주문만 새 이름을 가진다(M7 트랜잭션을 문서 계층에 연결하지 않았다).

## D3. 필드 추가 (주문에 배송 메모)

| 모델 | 쓴 KV 연산 | 쓴 바이트 | 시간 |
|---|---:|---:|---:|
| 관계형 (`ALTER TABLE ADD COLUMN`, 모든 행 재작성) | 20,002 | 0.8 MiB | 36.0 ms |
| 문서형 (새 문서 1개에만 필드) | 2 | 124 B | 0.2 ms |

관계형 행 인코딩은 "스키마 열 순서대로 값만"이라, 열이 늘면 기존 행을 새 스키마로 읽을 수 없어 전부 다시 쓴다. 문서형은 할 일이 없는 대신, 이후 모든 코드가 "memo가 없는 문서 20,000건"과 "있는 문서"를 함께 다뤄야 한다(M5 설계 §6의 필드 없음 규칙). **비용이 쓰기 시점에서 읽기 시점으로 옮겨 갈 뿐 사라지지 않는다.**

## D4. 저장 크기

| 모델 | 구분 | KV 항목 | 키 | 값 | 합계 |
|---|---|---:|---:|---:|---:|
| 관계형 | 행 (고객 2천 + 주문 2만 + 항목 6만) | 82,000 | 1.2 MiB | **2.9 MiB** | 4.1 MiB |
| 관계형 | 보조 인덱스 2종 | 80,000 | 1.8 MiB | 0 | 1.8 MiB |
| 관계형 | **합계** | 162,004 | | | **5.9 MiB** |
| 문서형 | 문서 (주문 2만) | 20,000 | 0.2 MiB | **3.8 MiB** | 4.0 MiB |
| 문서형 | 보조 인덱스 1종 | 20,000 | 0.4 MiB | 0 | 0.4 MiB |
| 문서형 | **합계** | 40,003 | | | **4.4 MiB** |

설계의 예상("관계형은 값만 저장하니 작다")은 **값만 놓고는 맞았다**(2.9 vs 3.8 MiB). 그러나:
- **정규화가 키를 늘린다.** 항목 6만 개가 각자 행 키를 가진다(1.2 MiB). 문서형은 항목이 주문 문서 안에 있어 키가 2만 개뿐이다.
- **JOIN이 인덱스를 요구한다.** 주문→항목, 고객→주문을 따라가려면 인덱스 2개(8만 항목, 1.8 MiB)가 필요하다. 문서형은 고객으로 주문 찾기용 1개면 된다.
- 행끼리만 보면 4.1 vs 4.0 MiB로 거의 같다. JSON의 필드 이름 비용과 정규화된 행의 키 비용이 비슷한 크기다.

## D5. 일관성 경계

[`ConsistencyBoundaryTest`](../../sql/src/test/kotlin/dev/mydb/sql/ConsistencyBoundaryTest.kt): 주문 INSERT 뒤 항목 INSERT가 (중복 키로) 실패하면 관계형에는 **항목 없는 주문**이 남는다. 원자성의 단위가 문장이고 주문·항목은 두 문장이기 때문이다. 문서형은 주문과 항목이 문서 하나라 그런 중간 상태가 없다. 관계형에서 이것을 막는 것이 M7의 다중 키 트랜잭션이다. **이후 SQL에 `BEGIN … COMMIT`을 연결했고**, 같은 상황을 `ROLLBACK`으로 되돌리는 테스트가 있다([`SqlTransactionTest`](../../sql/src/test/kotlin/dev/mydb/sql/SqlTransactionTest.kt) "여러 문장을 원자적으로 묶어 중간 실패를 되돌린다"). 이 측정의 수치는 비트랜잭션 모드 값이다.

## 정리

| | 관계형이 유리 | 문서형이 유리 |
|---|---|---|
| 읽기 | 여러 엔티티를 자유롭게 조합하는 질의 | 한 덩어리로 읽는 접근 (D1: 12배) |
| 쓰기 | 공유 데이터 변경 (D2: 쓰기 1건) | 덩어리 단위 원자성 (D5) |
| 스키마 변경 | 이후 읽기가 단순 | 변경 자체가 즉시 (D3) |
| 공간 | 값이 작다 | 키·조인 인덱스가 적다 (D4) |

어느 쪽도 공짜가 아니다. **데이터를 어떻게 읽고 바꾸는지(접근 패턴)가 모델을 고르는 기준**이라는 DDIA 2장의 결론을 같은 KV 엔진 위에서 숫자로 확인했다.
