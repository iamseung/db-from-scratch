# SSI 성능 비용: SNAPSHOT vs SERIALIZABLE

> 측정일 2026-10-26 · 재현: `./gradlew :bench:run --args=ssi` (절 하나만: `--args="ssi 2"`) · 코드: [`SsiBench.kt`](../../bench/src/main/kotlin/dev/mydb/bench/SsiBench.kt)
> 설계: [m7-transactions.md §11](../detailed/m7-transactions.md). 모두 M2 LSM(MANUAL) 위, 환경은 [M1 측정](m1-log-engine.md)과 같다.

## 요약

| 비용 | 결과 |
|---|---|
| 경합 없을 때 고정 비용 | 읽기 전용 **8% 느림**, 쓰기가 있는 트랜잭션은 0 ~ 2% (노이즈 수준) |
| 오래 열린 트랜잭션 | 상한이 없으면 하나만 열려 있어도 커밋 기록이 쌓여 **커밋이 1.9배**(10개면 2.4배) 느려지고 기록이 **무한히 늘어남** → **기록 상한(§11.7)을 추가해 보관 74개, 커밋 지연 SNAPSHOT 수준으로 해결** |
| 기록 상한의 대가 | 상한이 아주 작으면(10) 요약이 거칠어져 거짓 양성이 3배 |
| 경합 시 처리량 | 회차 간 변동(2 ~ 3배)이 SI·SSI 차이보다 커서 **비교 불가** |
| 정합성 | 쌍 제약 워크로드에서 SI는 3회 중 2회 제약 위반, SSI는 0회 |
| 거짓 양성 | 순환이 불가능한 워크로드에서 SSI가 불필요하게 중단: 사슬 8에서 커밋 2,400건당 **358회**(약 15%), 사슬 64에서 49회(약 2%) |

**측정을 바로잡은 기록**: 첫 실행에서는 "읽기 전용이 SSI에서 1.57배 빠르다", "쌍 제약 출금에서 SSI가 3.3배 느리다"가 나왔다. 둘 다 SNAPSHOT이 항상 먼저 실행된 **JIT 예열 순서 효과**였다. 1 · 3 · 4절을 3회 반복하며 매 회 실행 순서를 번갈아 바꾸고 중앙값을 쓰도록 고쳐 다시 쟀고, 아래가 그 결과다.

## 1. 경합 없을 때의 고정 비용 (단일 스레드, 키 1만 개, 트랜잭션 2만 개)

| 트랜잭션 모양 | SNAPSHOT txn/s (3회) | SERIALIZABLE txn/s (3회) | 중앙값 SSI / SI |
|---|---|---|---:|
| 읽기 전용 (get 10) | 33,836 / 51,863 / 53,418 | 44,671 / 47,835 / 49,373 | **0.92** |
| 읽기 + 쓰기 (get 10, put 1) | 15,724 / 17,959 / 17,678 | 17,386 / 17,620 / 17,637 | 1.00 |
| 쓰기 전용 (put 10) | 6,923 / 6,993 / 6,926 | 6,903 / 6,842 / 6,716 | 0.99 |
| 범위 + 쓰기 (scan 100, put 1) | 19,492 / 19,863 / 19,717 | 19,008 / 19,232 / 19,401 | 0.98 |

- 경합이 없으면 SSI의 추가 작업(읽기 집합 기록, 커밋 때 다른 트랜잭션과 비교)은 작다. 쓰기가 있는 트랜잭션은 커밋 배치 쓰기가 비용을 지배해 차이가 보이지 않는다.
- **읽기 전용만 8% 느리다.** SNAPSHOT 읽기 전용은 커밋 때 할 일이 없지만(종료 표시만), SERIALIZABLE 읽기 전용은 읽기 전용 이상 현상을 막으려고 커밋 검사를 하고 기록을 남긴다(§11.3). PostgreSQL이 `READ ONLY DEFERRABLE`로 이 비용을 없애는 이유다.

## 2. 오래 열린 트랜잭션과 커밋 기록 누적

쓰기 트랜잭션 4,000개(각각 get 1 + put 1, 서로 다른 키)를 차례로 커밋하는 동안, 키 100개를 읽은 트랜잭션 N개가 열려 있다. 읽은 키가 겹치지 않아 중단은 없다.

### 2.1 상한 없음 (첫 측정)

| 격리 | 열린 트랜잭션 | 앞 1,000건 커밋 평균 | 뒤 1,000건 커밋 평균 | 측정 끝 보관 기록 |
|---|---:|---:|---:|---:|
| SNAPSHOT | 0 / 1 / 10 | 29.7 / 27.1 / 30.3 µs | 14.5 / 14.3 / 15.4 µs | 0 |
| SERIALIZABLE | 0 | 30.5 µs | 14.6 µs | 0 |
| SERIALIZABLE | 1 | 45.4 µs | **27.7 µs** | **4,000** |
| SERIALIZABLE | 10 | 46.0 µs | **34.5 µs** | **4,000** |

(이 절은 격리 간 비교가 아니라 열린 트랜잭션 수 간 비교라 순서 교대를 하지 않았다. 앞 1,000건은 예열이 섞여 있다.)

- **오래 열린 SERIALIZABLE 트랜잭션 하나가 기록 정리를 막는다.** 커밋된 트랜잭션의 기록은 "그와 실행 기간이 겹친 트랜잭션이 끝날 때까지" 필요하다(그 트랜잭션과 rw 간선을 만들 수 있으므로). 열린 트랜잭션이 끝나지 않으면 그동안의 커밋 기록 4,000개가 전부 남는다.
- 커밋 검사는 보관 기록 수에 비례하므로 뒤로 갈수록 커밋이 느려진다(1개: 1.9배, 10개: 2.4배). 기록은 읽기·쓰기 키 집합을 들고 있어 메모리도 같이 는다.

### 2.2 기록 상한 추가 후 (§11.7, 2026-10-26)

| 격리 | 기록 상한 | 열린 트랜잭션 | 앞 1,000건 | 뒤 1,000건 | 보관 기록 | 요약된 기록 |
|---|---|---:|---:|---:|---:|---:|
| SNAPSHOT | - | 0 / 1 / 10 | 70.6 / 36.7 / 31.7 µs | 28.7 / 17.0 / 15.3 µs | 0 | 0 |
| SERIALIZABLE | 없음 | 0 / 1 / 10 | 32.1 / 39.2 / 32.2 µs | 16.2 / **24.5** / **37.4** µs | 0 / **4,000** / **4,000** | 0 |
| SERIALIZABLE | **100** | 0 / 1 / 10 | 28.2 / 35.3 / 31.9 µs | 14.4 / **18.2** / **17.3** µs | 0 / **74** / **74** | 0 / 3,927 / 3,927 |

(맨 처음 실행된 SNAPSHOT·0개 행은 예열 때문에 높다.)

- 상한 100이면 보관 기록이 74개에서 멈추고, 뒤 1,000건 커밋이 상한 없을 때의 24.5 · 37.4 µs에서 **18.2 · 17.3 µs로 SNAPSHOT 수준**으로 돌아온다.
- 넘친 기록 3,927개는 요약 기록 하나로 합쳐졌다(아래 5절에 그 대가).

## 3. 경합 (스레드 8, 스레드당 커밋 300건)

| 워크로드 | 격리 | 커밋/s (3회) | 커밋당 시도 | 쓰기 충돌 | 직렬화 실패 | 제약 (3회) |
|---|---|---|---:|---:|---:|---|
| 이체 (계좌 20개) | SNAPSHOT | 18,543 / 43,121 / 39,209 | 1.76 | 1,816 | 0 | 합계 보존 |
| 이체 (계좌 20개) | SERIALIZABLE | 25,198 / 40,863 / 37,652 | 1.63 | 1,516 | 0 | 합계 보존 |
| 쌍 제약 출금 (쌍 10개) | SNAPSHOT | 267,895 / 459,421 / 561,879 | 1.01 | 29 | 0 | **위반 2 / 0 / 1쌍** |
| 쌍 제약 출금 (쌍 10개) | SERIALIZABLE | 230,070 / 346,864 / 543,478 | 1.01 | 26 | 8 | 유지 |

- **처리량은 비교할 수 없다.** 같은 격리 안에서 회차 간 2 ~ 3배 차이가 나고(뒤 회차일수록 빠름 — 예열), 그 폭이 SI와 SSI의 차이보다 크다. 횟수 지표(시도·실패·위반)만 해석한다.
- **이체**: 읽은 계좌를 반드시 쓰므로 경쟁이 쓰기-쓰기 충돌로 잡힌다. 두 격리 모두 정합성이 같고 SSI만의 실패는 없다. 이런 워크로드에서는 SERIALIZABLE이 추가로 하는 일이 없다.
- **쌍 제약 출금**: 쌍의 두 값을 읽고 한쪽만 쓴다 — write skew의 전형. **SI는 3회 중 2회 실제로 제약이 깨졌다**(x + y < 0). SSI는 직렬화 실패로 그 경우를 중단해 3회 모두 지켰다. 필요한 중단은 커밋 2,400건당 약 8회뿐이다.

## 4. 거짓 양성 — 순환이 생길 수 없는 사슬 워크로드

트랜잭션 i는 키 c_i를 읽고 c_{i+1}에 쓴다(i는 무작위). rw 간선은 항상 인덱스가 큰 쪽 → 작은 쪽, wr 간선은 작은 쪽 → 큰 쪽이다. 둘을 섞어 순환을 만들려면 "B는 A의 커밋을 봤고 A'의 커밋은 못 봤다"와 "B'는 A'를 봤고 A는 못 봤다"가 동시에 성립해야 하는데, 이는 A와 A'의 커밋 순서가 서로 반대여야 해서 모순이다. 따라서 **이 워크로드의 직렬화 실패는 모두 불필요한 중단**이다. 같은 키 쓰기 충돌은 두 격리 모두 정상이다.

| 사슬 길이 | 격리 | 커밋/s (3회) | 커밋당 시도 | 쓰기 충돌 (정상) | 직렬화 실패 (거짓 양성) |
|---:|---|---|---:|---:|---:|
| 8 | SNAPSHOT | 22,221 / 62,174 / 69,088 | 1.47 | 1,128 | 0 |
| 8 | SERIALIZABLE | 22,841 / 42,249 / 60,179 | 1.51 | 899 | **358** |
| 64 | SNAPSHOT | 97,864 / 141,421 / 156,156 | 1.08 | 199 | 0 |
| 64 | SERIALIZABLE | 106,494 / 110,283 / 131,588 | 1.10 | 180 | **49** |

- 사슬 가운데 트랜잭션은 "읽은 키를 앞 트랜잭션이 쓰고(나가는 간선), 쓴 키를 뒤 트랜잭션이 읽는다(들어오는 간선)" — 순환이 없어도 피벗 모양이라 중단된다. SSI가 순환 대신 위험 구조를 끊기 때문에 생기는 비용이다.
- 키가 적을수록(사슬 8) 같은 이웃끼리 자주 겹쳐 거짓 양성이 커밋의 약 15%까지 늘고, 키가 많으면(사슬 64) 약 2%로 준다. 경합이 심한 핫스팟일수록 SSI의 불필요한 재시도가 커진다.
- 이 구현은 순환이 아닌 위험 구조를 더 걸러 내는 PostgreSQL의 추가 조건(T_out이 먼저 커밋했는지, 읽기 전용 최적화 등)을 일부만 갖고 있어 실제 PostgreSQL보다 거짓 양성이 많을 수 있다(비교는 하지 않았다).

## 5. 기록 상한의 대가 — 거짓 양성 (사슬 64 + 오래 열린 트랜잭션 1개, 스레드 8, 1회)

| 기록 상한 | 커밋/s | 커밋당 시도 | 쓰기 충돌 | 직렬화 실패 (거짓 양성) | 보관 기록 | 요약된 기록 |
|---|---:|---:|---:|---:|---:|---:|
| 없음 | 15,346 | 1.13 | 235 | 77 | 2,400 | 0 |
| 1,000 | 25,121 | 1.10 | 190 | 49 | 898 | 1,503 |
| 100 | 37,202 | 1.09 | 159 | 51 | 55 | 2,346 |
| 10 | 45,863 | 1.17 | 157 | **241** | 7 | 2,394 |

- 요약 기록은 합친 기록들의 키를 범위 하나로 덮는다. 상한이 **10**이면 거의 모든 기록이 요약에 들어가 사슬 전체를 덮는 범위가 되고, 거짓 양성이 3배로 늘었다.
- 상한 없음·1,000·100 사이의 거짓 양성 차이(49 ~ 77)는 1회 측정의 노이즈 범위로 본다.
- 처리량은 상한이 작을수록 높게 나왔지만 이 절은 1회 측정이고 "상한 없음"이 먼저 실행돼 예열 효과가 섞였을 수 있어 해석하지 않는다. 보관 기록이 적을수록 커밋 검사가 짧아지는 효과(2.2절)는 있다.
- 기본값 1,000은 2절의 누적 문제를 막으면서 요약이 드문 쪽이다. 거짓 양성이 문제면 키우고, 메모리가 문제면 줄인다.

## 정리

| 질문 | 답 |
|---|---|
| SSI는 평소에 비싼가 | 아니다. 경합이 없으면 0 ~ 8% |
| 언제 비싼가 | (1) 오래 열린 SERIALIZABLE 트랜잭션이 있을 때 — 상한 없이는 기록이 쌓여 모든 커밋이 느려지고 메모리가 는다(상한으로 해결, 대신 요약에 의한 거짓 양성) (2) 핫스팟 경합 — 순환이 없어도 위험 구조로 중단(거짓 양성)되어 재시도가 는다 |
| 무엇을 얻는가 | write skew·phantom·읽기 전용 이상 현상이 실제로 일어나는 워크로드에서 정합성 (쌍 제약: SI 3회 중 2회 위반 → SSI 0회) |
| 언제 SNAPSHOT으로 충분한가 | 읽은 것을 반드시 같이 쓰는 트랜잭션(이체처럼) — 경쟁이 쓰기-쓰기 충돌로 이미 잡힌다 |
